# delta-harness — known product bugs (follow-up)

Genuine OpenHouse/Iceberg behavior bugs surfaced by the harness. Each is tagged in
`Plan.knownBugs` (so its case reports `SKIP (bug: …)` instead of failing the suite) and listed
here for follow-up. A tagged case is a **deferred bug**, not a passing test — do not build further
coverage on top of the broken behavior.

| Case (id substring) | Reason | Found | Follow-up |
|---|---|---|---|
| ~~`insert.explicitColumns`~~ **RECLASSIFIED → negative PIN (not a bug)** | `INSERT INTO t (foo_col_long, foo_col_string) VALUES …` is rejected with `INCOMPATIBLE_DATA_FOR_TABLE.CANNOT_FIND_DATA`. **Code-verified (bug investigation): this is an ENGINE limitation, not OpenHouse.** OpenHouse creates columns **nullable-by-default** (`CTASNonNullTestSpark3_5:30-33` — only explicit `NOT NULL` is preserved) and the server round-trips the schema **verbatim** (`OpenHouseTableOperations:210` → `OpenHouseInternalTableOperations:234-246`); no requiredness is injected. The reject comes from Spark's byName `TableOutputResolver` because Iceberg 1.5's `SparkTable` does **not** implement `SupportsColumnDefaultValue`, so no NULL-fill projection is inserted for omitted columns. Identical with or without OpenHouse. | Phase 4 | **DONE — reclassified** to a negative pin (`insertExplicitColumns` asserts the `CANNOT_FIND_DATA` rejection; removed from `knownBugs`). The pin flips if the stack gains column-default support (Iceberg ≥ 1.7) — then restore null-fill. |
| `nested.deleteByNestedField` | `DELETE FROM t WHERE s.x = 2` (predicate on a nested struct field) fails with `[INTERNAL_ERROR] … NullPointerException`, across parquet/orc/avro. `SELECT … WHERE s.x = 2` and `UPDATE … SET s.x = …` on the same field both succeed, so it's specific to the DELETE plan. | Phase 6 | **Code-verified UPSTREAM** (not OpenHouse): the row-level DELETE rewrite is owned entirely by `IcebergSparkSessionExtensions` + Spark's optimizer; OpenHouse's parser delegates non-policy SQL straight to Spark and adds no rewrite rule. The NPE is in the nested-field DELETE-rewrite plan. **Still tagged SKIP.** Follow-up: capture the full cause-chain stack (the harness only surfaces the top-level NPE), reproduce on clean Apache Iceberg 1.5.2 + Spark 3.5.2 vs the `com.linkedin.iceberg` 1.5.2.15 fork, then file upstream. |
| `ddl.encryption` | Encryption is **not implemented in OSS** — a repo-wide search finds no `EncryptionManager` / `KeyManagementClient` / parquet crypto factory / interface / mock; the `encryption()` hook is un-wired, so data is written **plaintext** on disk. The KMS plugin lives in a **private repo**. The `ddl.encryption.active` test asserts the intended behavior (data file NOT plaintext when encryption is configured) and is tagged SKIP. | Phase 24b (DDL) | Not a bug in OSS per se — a **capability gap**: encryption is delegated to an external plugin. Unskip once the private KMS plugin is wired (override `encryption()` / set `parquet.crypto.factory.class`); the test then validates encryption-ON (ciphertext on disk, unreadable without a key). |
| `ddl.renameColumn` ⚠️ **GENUINE OpenHouse regression** | `ALTER TABLE t RENAME COLUMN a TO b` is a **silent no-op** — neither errors nor renames, across parquet/orc/avro. `ADD COLUMN` and type-widen work. | Phase 13 (DDL) | **Code-verified ROOT CAUSE — regression from PR #558 (commit `0ad4914`, 2026-05-01, "make OH reads/writes case-insensitive").** The rename DOES reach the server; `doUpdateSchemaIfNeeded` calls `normalizeSchemaCasingToTable(writeSchema, tableSchema)` unconditionally (`OpenHouseInternalRepositoryImpl:588-591`), which rewrites every field's name to the table's spelling **matched by field ID** (`BaseIcebergSchemaValidator:60-73`) — for the renamed field (same ID, new name) it sets the name back to the old one, erasing the rename. Because that runs **before** the `!sameSchema` gate (`:592-608`), the schema now looks unchanged → returns with no update, no validation, no error. `validateWriteSchema` (which would reject loudly, `:151-160`) never fires. Pre-#558 this was a clean rejection. **Fix:** guard the normalizer with `original.name().equalsIgnoreCase(tableField.name())` so it only fixes case, not renames (→ restores a loud rejection); to actually SUPPORT rename, also match `validateFields` by field ID and relax the `entriesDiffering` branch (`:129-135`). Un-tag the test once fixed; if "reject loudly" is chosen, flip to a negative test asserting `InvalidSchemaEvolutionException`. **This is a production-code fix — out of scope for this test PR; flagged for a separate change.** |
