# Behavior-change ledger against LinkedIn main

The owner's rule, S60 (2026-11-27), verbatim: "This is a hard requirement in that this can't be contributed upstream
given behavior changes without sufficient justification. it's not a two say door to change behavior. it is a two way
door when it's documented for follow up and not a foundation decision that invalidates significant work. significant
is a judgement call, but if a single agent can fix it with a single pull request less than a couple thousand lines
with <20 files it's easily fixable."

Bottom line (updated 2026-11-28: 55 rows; parts D and E and the status of the restored rows are at the end, and the counts are re-done): the nine retroactive reviews of 2026-11-27 found 43 distinct behavior changes against LinkedIn main
`bb8929e1` that a deployment sees without changing its configuration. 26 of them are visible on the reference line
(`-PicebergLinkedIn`), which was meant to be LinkedIn main's build unchanged; so the reference line does not prove
today that LinkedIn's deployment is unaffected. 24 of those 26 are SMALL and none has the owner's justification, so
under S60 each is restored (12), gated (4), or kept only as a fix of a real defect on main with its justification
written down (8). The other two (the deleted Iceberg 1.2 / Spark 3.1 line and `libs:datalayout`) need the owner. Seven
rows in all are OWNER: they follow from deleting that line or from moving to Iceberg 1.12 and Java 17, and he was never
told those consequences. Ten rows are changes to CI, the release workflow, the build mechanics and the published test
fixtures; the worst is that LinkedIn's release workflow now pushes a tag and then publishes nothing.

## How to read the tables

Bottom line: each row is one behavior change merged across reports; its id is stable and other notes cite it.

- What existed: the surface: native tables API, House Tables, Spark SQL through the existing catalog, a maintenance job,
  the Java client, a shipped artifact, the build, a CI workflow.
- Line: which build line shows the change, and how that is known. "Both" means the changed file is compiled on both
  lines and nothing in it checks the line. Code under `services/tables/src/iceberg-1.12` compiles only on the default
  line (`services/tables/build.gradle:104-121`, BD B26); everything else in `services/`, `iceberg/openhouse/`,
  `integrations/spark/spark-3.5/`, `apps/spark-3.5/` and `libs/` is compiled on both lines.
- Size: SMALL (one agent, one pull request, under about 2,000 lines and 20 files) or FOUNDATION, with what undoing it
  would invalidate.
- Disposition: RESTORE (put main's behavior back), GATE (keep the new behavior behind a property whose default
  reproduces main), KEEP-FIX (it fixes a real defect on main: keep it, write its justification in the code and the merge
  record, and offer it upstream as its own small change), KEEP-DIRECTED (the owner directed it), OWNER (needs the owner;
  the exact question is in the row).
- "Ready" in a disposition means the orchestrator has already decided it (three items, listed in
  `86-review-findings-and-fix-forward.md`).
