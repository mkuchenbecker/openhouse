## The jobs batch (X11, X12, X13, pull request 145)

Full suites on head `a76d7827`, JDK 17 [ran; tests, failed, skipped]: 1.12 line 481/0/5; Spark 4.2 jobs 482/0/5; 1.5.2 line
481/1/91. CI on the pull request passed (13 jobs, 1 skipped by design).

- X11, the cause [read, ran]: sort stats collection on a format v2 table on the 1.5.2 line failed with "Cannot parse order:
  parser is not an Iceberg ExtendedParser" and rewrote nothing. Iceberg 1.5.2's sort-order parsing requires Iceberg's parser
  to be the session's outermost parser. With Iceberg's extensions listed first and OpenHouse's second, OpenHouse's parser
  is outermost and delegates to Iceberg's. Iceberg 1.12 walks the delegates, so that line never failed.
- X11, fixture against production [ran]: a new test reads the repository's job configuration (`jobs.yaml` in the
  docker-compose recipe, the only one in the repository) and asserts the test session has the same extensions in the same
  order and the same openhouse catalog. The scheduler adds only the table name and the token [read]. So the fixture is not
  the cause, and a 1.5.2 deployment with that order failing the same way is inferred, not observed.
- X11, the fix [ran]: if Iceberg's own parse works on the session (1.12 on both Spark lines) the job makes the same SQL
  call with the same text as before. Otherwise, if an Iceberg parser sits below the session's parser, the job parses the
  sort order with it and runs the same rewrite through Iceberg's action with the same options, which is what the 1.5.2
  procedure's body does. With no Iceberg parser at all it fails as before. On 1.5.2 the job now completes and sets its
  property (0.73% in the test). Differences from the procedure: no cache refresh of the temporary table (dropped right
  after) and no procedure output rows (unused). On 1.12 and Spark 4.2 there is one extra in-memory parse per run.
- X11, not taken: reordering the extensions in `jobs.yaml`, a deployment change whose effect on OpenHouse's own SQL
  commands is untested; and a table-level sort order on the temporary table, which would add a commit to the service.
- X11, proof [ran]: the sort stats case asserts success on v2 on 1.5.2 and on v2 and v3 on 1.12 and Spark 4.2.
  `SortStatsParserTest` (6 cases on all three lines) asserts which path each line takes, the parsed order, one sorted
  file and the same rows.
- X12, the suspected over-count does not exist [read, ran]: the collectors select content, path and size, drop duplicate
  file paths, then count and sum. Every deletion vector in one Puffin file carries that file's path and whole size, so
  they are one row. A test pins it: a v3 table with 8 deletion vectors in 4 Puffin files reports 4 files and 5381 bytes
  (counting per vector would give 8 and 13327); v2 numbers are as before. No code change, no stats schema change.
- X13, nothing needs fixing [read, ran]: a DELETE that races a retention run leaves a deletion vector pointing at a data
  file retention removed. It is harmless: rows, row ids, every referenced file and the stats are right, and compaction and
  expiry leave it. The next retention run removes it (a delete commit with one vector removed). A test runs the race, then
  compaction, then expiry, then a second retention run. If the policy is lengthened or removed first, the vector stays,
  still harmless [inferred]. Cost until then: one entry and its share of the Puffin bytes.
