# V1 inventory: every write that reaches persisted table metadata, and the rules on the way

Base: `origin/irc/v2-irc-read-endpoints` at a2edc223 (worktree `/home/user/oh-v1`). All file:line references are
to that commit. Read, not run, unless a line says otherwise.

Abbreviations: `TSI` = `services/tables/.../services/TablesServiceImpl.java`; `ISSI` =
`.../services/IcebergSnapshotsServiceImpl.java`; `REPO` = `.../repository/impl/OpenHouseInternalRepositoryImpl.java`;
`OPS` = `iceberg/openhouse/internalcatalog/.../OpenHouseInternalTableOperations.java`; `CAT` =
`.../internal/catalog/OpenHouseInternalCatalog.java`; `VAL` = `.../api/validator/impl/OpenHouseTablesApiValidator.java`;
`SVAL` = `.../api/validator/impl/IcebergSnapshotsApiValidatorImpl.java`. Tests: `CP*` = `e2e/h2/CommitPath*Test`.

"Pair-statable" means the rule can be stated over (base `TableMetadata` as stored, candidate `TableMetadata`, request
context) without losing anything the rule reads today. "Context" is what metadata cannot carry: principal, declared
capabilities, column-default bypass, the native operation kind, structured policies, table type, snapshot payload text.

## 3. Rules that cannot be stated over (base metadata, candidate metadata, context) without loss

1. **S9, the native no-op short-circuit.** It compares the native request, field by field and as text, with the stored DTO view, including `baseTableVersion` against the stored `openhouse.tableVersion` (the previous location). Two requests that describe the same candidate metadata can get different outcomes (one returns 200 with no write; one goes on to R12 and R23). Needs: the native request DTO. It stays native-specific; in V1 the native decoder passes it to the core as an optional "no-op test" in the context.
2. **R13 and R11 read the request's reserved keys as sent.** Over a pair they are statable only if the candidate's properties are the request's properties, reserved keys included, not the properties that will be stored (the reserved keys the native client echoes are never applied; the server stamps them). For IRC the natural candidate (base plus `SetProperties`) has the same shape, so the rule reads the same.
3. **Policies are a second channel.** The stored `policies` property is reserved (R13: the raw key may not change) and is replaced from the structured `policies` field (R19, S5, S12, R9). A single candidate property map cannot say "unchanged raw key, new structured value". Needs: context policies. IRC: none (keep stored) until a decision says how IRC changes policies.
4. **Table type** (R14, S7 for replicas, V7) is a request field with a default, stored as `openhouse.tableType`. Needs: context table type (or read from the candidate's reserved key).
5. **The snapshot payload.** Native snapshot PUTs carry snapshot JSON text that is parsed only in P9, after P3, P5, P6 and P7. A candidate with parsed snapshots would move the parse (and its 500/400/409 classification) ahead of the authorization, lock, version and retry-cache checks, and would stop P7 from burning the base version of an unparseable request. Needs: the payload text in the context, parsed where it is parsed today.
6. **Schema text.** S13 operates on JSON text, and R16's message embeds the request schema JSON as sent (after S13). Over metadata the schema is an object; the message would read the same only if the candidate schema is serialized the same way. Needs: the schema as text (for native: as sent; for metadata: `SchemaParser.toJson`).
7. **Construction order.** Iceberg's `TableMetadata.Builder` rejects some invalid candidates itself, before any OpenHouse rule could: a schema that drops a partition source column fails `PartitionSpec` re-binding with `ValidationException`, where today the native PUT gets R15's 400 "Adding partition spec failed:Cannot find source column" (pinned in `CPInvariants.incompatibleSchemaChanges...`). So the native decoder cannot build a `TableMetadata` up front without changing which error a bad request gets. Needs: the native candidate's parts evaluated lazily, in the order the rules ask for them.
8. **Operation kind.** S5 and S9 apply to table PUT only; S6's message and S14's 409/503 wording differ between table PUT and snapshots PUT. Needs: the native operation kind in the context.
9. **Replace / RTAS and staged flags** (S2, R3, R8-R10, staged-create HTS skip) are intents, not metadata. Needs: context.
10. **Extension points typed on `TableDto`**: `PreservedKeyChecker.isKeyPreservedForTable(key, TableDto)` (with the `@PreservedPropsToggleEnabler` aspect), `TablePolicyManager.managePoliciesOn*(..., TableDto, ...)`, `PoliciesSpecMapper.toPoliciesJsonString(TableDto)`, `PartitionSpecMapper.toPartitionSpec(TableDto)`, `ReadBridgeStripProtection.prepare(TableDto)`, `AuthorizationUtils.*(TableDto, ...)`. Statable over the pair as rules, but the deployed overrides receive a `TableDto`, so the core must hand them one. Needs: a `TableDto` view of base and candidate.

## 4. What the update commit reads, summarized

For an update commit on an existing table, the rules read exactly: from the base, its properties (reserved keys, `policies`, user props, `history.expire.max-ref-age-ms`, `required-capability.*`), schema, default spec, sort order, metadata location; from the candidate, schema (as object and as text), intermediate schemas (replication), partition spec, sort order, properties as requested; from the context, principal, operation kind, structured policies, table type, snapshot payload text and refs, declared capabilities and the column-default bypass (request-scoped beans), the action-type declaration (request header) and, for table PUT, the native no-op test.

The update path persists only: current schema (plus intermediate schemas), sort order, user properties, `policies`, the table-type back-fill, snapshots and refs. It never writes a partition spec, location, UUID, statistics, or format version (format version changes only through a `format-version` user property, which Iceberg's `replaceProperties` turns into an upgrade).
