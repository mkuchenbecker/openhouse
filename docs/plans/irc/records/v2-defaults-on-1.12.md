# Column defaults on v2 OpenHouse tables: what changes on the 1.12 line

**Bottom line: partly safe.** LinkedIn never stores defaults in Iceberg metadata. The server keeps them outside Iceberg, sends them in the per-table `config` map, and the client overlays them in memory. 1.12 accepts that overlay. `TableMetadataParser.fromJson` has no format-version check on defaults. So loading, scanning, appending, property changes, snapshot management and RTAS all work on a v2 table. With the ported patches, Spark 3.5 ORC reads (row and vectorized) fill the default; I ran this. **One thing breaks: any schema change made from a client that holds an overlaid v2 table.** That includes ALTER TABLE ADD COLUMN, rename, doc changes and merge-schema writes. 1.12 rechecks the whole new schema in `TableMetadata.Builder.addSchemaInternal`. The overlaid defaults on the existing fields then fail with `IllegalStateException: Invalid schema for v2: - Invalid initial default for country: non-null default (US) is not supported until v3`. This happens on the client, before `doCommit`, so the server's strip step never runs. The porting job's claim is true only for paths that add a schema (create, addSchema, updateSchema). It is not true for parsing. Its tests failed because they created tables with defaults in the schema, which LinkedIn's flow never does. One more change: on 1.12, Parquet and Avro reads also fill overlaid defaults. On LinkedIn 1.5.2 they return NULL.

## 1. How defaults reach readers today (OpenHouse main, read)
- Storage: defaults come from a deployment bean, `ColumnDefaultsSource.defaults(TableDto)` (readbridge/ColumnDefaultsSource.java). They apply only when the table property `required-capability.column-defaults=true` is set (ReadBridgeConfigResolver.java:91-109).
- Delivery: `ReadBridgeConfigResolver.resolve` (line 49) turns them into `config` entries `openhouse.read-bridge.column-default.<fieldId> = <single-value JSON>`. `OpenHouseTablesApiHandler.java:48` attaches that map to the GET response.
- Persist: the server strips every `initial-default` before saving. That is `ReadBridgeStripProtection.prepare` (lines 78, 198), called from TablesServiceImpl.java:197 and IcebergSnapshotsServiceImpl.java:96. ReadBridgeColumnDefaultE2ETest:204-228 asserts the stored schema has no `initial-default`. So the metadata file never carries defaults.
- Format: tables are v2 by default (`cluster.iceberg.format-version:2`, ClusterProperties.java:46). The server sets this at OpenHouseInternalRepositoryImpl.java:769-771.
- Client overlay: `OpenHouseTableOperations.doRefresh` (lines 129-169) passes `loadMetadata` (lines 178-191) to `refreshFromMetadataLocation`. `loadMetadata` calls `TableMetadataParser.read(io, location)` and then `ReadBridge.apply` (ReadBridge.java:66-94).
- `apply` does `TableMetadataParser.toJson(raw)`, then Jackson sets `initial-default` on each field with a matching id in every entry of `schemas[]` (nested fields too), then `TableMetadataParser.fromJson(raw.metadataFileLocation(), json)`. **The overlay builds a whole new `TableMetadata` through the parser.** This metadata becomes `ops.current()`, so Spark's `table.schema()` and every later commit base carry the defaults.
- Write back: the client sends `SchemaParser.toJson(metadata.schema())` (OpenHouseTableOperations.java:278), defaults included. The server strips them. `ColumnDefaultCommitPolicy.check` (lines 58-64) runs as a pre-commit check (OpenHouseInternalTableOperations.java:678-679).

Smallest changes that keep LinkedIn's e3 behavior (descriptions only, none tried):
1. LinkedIn Iceberg patch: skip the `initial-default` part of `Schema.checkCompatibility` for v2 when called from `addSchemaInternal`, restoring 1.5.2 behavior. Gate it behind a flag or table property so other catalogs keep the v3 rule. It is one condition, but it lets non-OpenHouse writers persist defaults in v2 files if the gate is open.
2. OpenHouse client only: give schema updates a base without the overlay. For example, `OpenHouseTable.updateSchema()` could return an update built on the raw (un-overlaid) metadata, or strip `initial-default` from the applied schema before `updateSchema`. More code, no Iceberg patch.
3. Move bridged tables to v3. Defaults are then legal everywhere, but every reader must handle v3, and the `iceberg-1.2` runtime cannot. That is the biggest change.

## 5. Parquet (and Avro) on the new line
- 1.5.2 (li/openhouse-1.5.2): `initialDefault` is used only in `Types`, `SchemaParser`, the ORC files and Spark 3.5 `OrcSchemaWithTypeVisitorSpark`, `BaseRowReader` and `SparkBatch` (`git grep`). Spark Parquet and Avro readers return NULL for a missing optional column. OpenHouse's `parquetBackfillsColumnDefaultsViaReadBridge` is `@Disabled` for that reason (ColumnDefaultSparkITest:108-114).
- 1.12: `ParquetValueReaders.defaultReader` (lines 272-287) fills the default. `SparkParquetReaders` reaches it through `structReader` (line 153). The vectorized path fills it in `VectorizedReaderBuilder.defaultReader` (arrow, lines 128-138). Avro fills it in `avro/ValueReaders.java:315`. Row-group filtering accounts for it in `ParquetMetricsRowGroupFilter.java:140-150`. None of these check the format version.
- Ran: v2 Parquet table with an overlaid default, row and vectorized. Rows were `[1,US],[2,CA],[3,null]` and `country='US'` returned id 1. **So Parquet reads differ from LinkedIn 1.5.2: rows from older files now show the default instead of NULL.** That is what the disabled OpenHouse test wants, but it is a visible change for any opted-in Parquet table.

## Enforcement points in 1.12 (all one check)
- `Schema.DEFAULT_VALUES_MIN_FORMAT_VERSION = 3` (api/.../Schema.java:61). `Schema.checkCompatibility(schema, formatVersion)` (lines 604-636) collects one problem per field with a non-null `initialDefault` when the version is below 3 (line 619), checking all nested fields. It throws `IllegalStateException("Invalid schema for v<N>:\n- Invalid initial default for <col>: non-null default (<v>) is not supported until v3")`. It does not check `write-default`.
- Its only caller is `TableMetadata.Builder.addSchemaInternal` (core/.../TableMetadata.java:1614-1621). That runs from `setCurrentSchema(Schema,int)` (1093), `addSchema` (1136), `TableMetadata.updateSchema` (602-606, used by `SchemaUpdate.commit`) and `newTableMetadata` (148-150, table creation).
- Not checked: `TableMetadataParser.fromJson`, the `TableMetadata` constructor, `Builder.build()` (it checks only spec and sort-order compatibility, lines 1569-1570), `setCurrentSchema(int)`, `SchemaParser`, `SchemaUpdate.apply()`, and the readers.
- 1.12 also adds `UpdateSchema.addColumn/addRequiredColumn(..., Literal)` and `updateColumnDefault` (UpdateSchema.java:109ff; SchemaUpdate.java:322). They are checked only through the builder at commit.
- LinkedIn 1.5.2: there is no `Schema.checkCompatibility` (`git show li/openhouse-1.5.2:api/.../Schema.java`, no match). `addSchemaInternal` (TableMetadata.java:1490) checks no defaults. So none of these points exist there.
