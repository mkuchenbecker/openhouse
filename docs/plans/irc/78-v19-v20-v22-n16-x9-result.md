## A. The tables-service batch (pull request 142)

Bottom line: the rename target limit is now a cluster property, a table on its own storage type gets its own FileIO
class in Iceberg REST responses, and the last Iceberg 1.2 leftover is gone. Nothing changes by default.

### V19: the rename target limit

- Defect [ran]: the House Tables table id column is 255 wide in the production schema and 128 in the bootstrap
  `schema.sql`. On a store made from `schema.sql`, a rename to a name of 129 to 255 characters failed with 500 after its
  metadata file was written, and the file stayed. A pin test showed it on both the native and the Iceberg REST rename.
- Fix: `cluster.housetables.table-id-max-length`, default 255, next to the metadata location property of pull request
  121 and documented with it in `DEPLOY.md`. With 128, a longer target is refused with 400 on both rename routes before
  anything is written: no row, no file, the table unchanged, and a later valid rename works [ran]. A value that is not
  positive means the default.
- Why a property and not create's 128-character rule (option b): that rule would refuse renames that work today on a
  production-schema cluster, which is a behavior change for every such cluster.
- Nothing changes by default: a 255-character target still succeeds and 256 is refused [ran]. A cluster that sets the
  property gets a 400 where it got a late 500.

### V20: the FileIO class of a table's own storage type

- Defect [ran]: the Iceberg REST config route advertised the FileIO class of the cluster's default storage type, so a
  table the cluster places on another type was read through the wrong class by an unmodified client.
- What a client receives and uses: a load, create, commit, register or staged-create response carries `io-impl` in its
  config when the table's storage type has a known class that differs from the default's. Both client lines lay a
  table's config over the catalog's properties when building its FileIO [read] (1.12 source, 1.5.2 bytecode).
  - A local table on an s3-default cluster: the response carries `HadoopFileIO`, and a real `RESTCatalog` reads the table
    and commits an append through it [ran]. Before, the config was empty and the client used `S3FileIO`.
  - A local table on an hdfs-default cluster: config empty, as before, because hdfs and local share one class [ran].
  - A table on the default storage: byte-identical responses. A storage type with no known class: no entry.
  - An s3 or adls table on an hdfs- or local-default cluster: that type's class, by the unit test of the mapping only.
- Only the class name is sent: no endpoint, bucket, account or credential. The native API is untouched.
- Not run: one direction only was run end to end (the local table on an s3-default cluster). The S3 and ADLS directions
  rest on `IcebergRestTableFileIoTest` (4 tests, every pair and an unknown type); no S3 or ADLS store is reachable here
  and no client was run reading through `S3FileIO` or `ADLSFileIO`.

### V22: the last Iceberg 1.2 leftover

- Removed: `ViewsDisabledService` and the choice between it and `ViewsServiceImpl`, which is now registered
  unconditionally, with four tests whose only subject was that choice.
- Stays: the per-database views gate (`ViewsFeatureGate`), a real feature. No route answers differently [ran: view
  route, service and pagination tests on both lines; the endpoint list test unchanged].

## B. The jobs fix (pull request 141)

Bottom line: `Operations` builds its catalog once on first use, reuses it for the job run and closes it in `close()`.
Behavior is unchanged where it was checked, and the leak per table load is gone. The pool per job run is not.

### N16: the defect and the fix

- Defect [read, ran]: `Operations.getTable` built a new catalog on every call. On the Spark 3.5 line each OpenHouse
  catalog's client keeps a connection pool that is never disposed, so a long batched job grew without bound and the
  jobs test process ran out of memory in CI (pull request 137). On Spark 4.2 each new `RESTCatalog` sent `GET /config`.
- Pinned observable [ran]: `OperationsCatalogTest`, committed first: 300 table loads plus one expiry built 301
  catalogs; with the fix, 1. Run on the 1.12 line, with `-PicebergLinkedIn` and on the Spark 4.2 jobs line.
- Level of the fix: the jobs, not the Java client. A client change alters pool lifetime and limits for every other user
  of the client, so it was not made (see the two unsolved items).
- Production constructs `Operations` in `BaseSparkApp.run` only, and closes it there [read]. `getCatalog` is
  synchronized because batched apps load tables from a thread pool, which now share one catalog and one pool, as
  Spark's SQL catalog already does. A failure closing the catalog is logged at WARN and not thrown.

### What was checked to stay the same

- Freshness [read, ran]: neither catalog keeps tables. The OpenHouse catalog has no table cache, and the fork's
  `RESTCatalog` caches only on an ETag, which the tables service never sends. A test on all three lines shows the next
  `getTable` on the same `Operations` sees a snapshot, a schema change and a property change committed by other clients.
- Requests [read]: on Spark 3.5 each load is still one GET and catalog setup sends none. On Spark 4.2 `GET /config`
  goes from one per load to one per job run. Not counted on the wire: the 4.2 test service has no access log, so the
  claim rests on the catalog count and on reading the code.
- Authentication [read, not run]: both catalogs read the token once, when built, from the Spark session properties, and
  nothing refreshes it in a run, so reuse changes nothing about how a long job picks up a token. On the REST line, fewer
  failed token-exchange attempts when a JWT expires mid-run (the service does not serve that route, so the outcome is
  the same). The expiring-JWT behavior was read, not run.

### X9: a signal for delete files in backups

- When the expired partitions of a backup-enabled table carry delete files, retention logs a WARN line with the counts
  and emits `retention_backup_delete_file_count` through the emitter the retention path already uses, with the table
  name and the kind (position deletes, equality deletes, deletion vectors). Nothing is emitted when no expired data
  file carries deletes. No refusal; what is backed up and deleted does not change. D46 stays Mike's.
- Observed [ran]: v2, 4 position-delete files; v3, 4 deletion vectors; of 6 expired data files. A new case asserts
  nothing fires without delete files. Not exercised: equality deletes through retention with a backup.

### Not solved

- One OpenHouse client connection pool per job run, and one per Spark session, lives until the process exits: the
  client has no close, and on 1.12 the catalog's close only closes its metrics reporter. Releasing or sharing the pool
  is a change to the Java client for all its users, so it needs Mike's say (new item N17).
- The jobs test suite's heap margin is unchanged at about 140 MB of 512. The remaining pools come from the tests' own
  Spark sessions and from fixtures that build a new `Operations` per call. New jobs tests can still run it out of memory
  (new item C19, in flight).
