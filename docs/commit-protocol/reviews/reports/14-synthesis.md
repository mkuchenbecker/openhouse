## Part 1 — Review body (to post verbatim)

The fix is sound and the evidence is real: the guarded rename is implemented
faithfully end to end for token-carrying callers, the committed TLC logs
reproduce bit-for-bit (violation traces and the clean 6,130-state guarded
run), the two race partitions are tested with forced interleavings, and the
hot commit path is untouched. No code change is demanded. What blocks is
documentation accuracy in `specs/tla/`: the verification claims overstate

## Part 2 — Comment set (post verbatim, one per location)

### Comment 1
- path: specs/tla/README.md, line 16 (RIGHT)
- body:

[tla-review][blocking] "All invariants hold" is true of the model but wider
than what the code ships. `RenameHtsGuarded` always carries the caller's
base (`rBase`), yet the implementation also ships a token-absent mode —
callers that omit `expectedMetadataLocation` (old clients mid-rollout), and
the `INITIAL_VERSION` fallback in `OpenHouseInternalTableOperations` for
legacy tables with no persisted `tableLocation` — whose guard is only the
version CAS between the HTS service's own read and UPDATE. In that mode a
commit landing between the renamer's load and the HTS read is still
silently overwritten: the modeled `RenameHtsUnguarded` outcome in a
narrower but non-empty window. TLC's clean pass therefore covers the
token-present mode only. Smallest fix: scope this row and the spec-header
claim to the token-present mode and name the residual null-token window
(the PR body's Additional Information already concedes it). Follow-up
option: model the token-absent mode as a third rename action — TLC will
produce the residual counterexample, which is the honest artifact and
documents why the internal catalog always sends the token.

### Comment 2
- path: specs/tla/OpenHouseCommitRename.tla, line 29 (RIGHT)
- body:

[tla-review][blocking] The header (and the README's guarded row) describe
the fixed UPDATE as "conditional on the row still being at the renamer's
loaded state (expected metadataLocation + @Version)". The JPQL conditions
on `@Version` only (`AND table.version = :expectedVersion`); the expected
metadataLocation is checked earlier and non-atomically, at the service's
`findById` (UserTablesServiceImpl). Collapsing that two-step guard into the
model's atomic `catLoc = rBase` is sound if and only if every
`UserTableRow` mutation bumps `@Version` — true today (`renameTableId` is
the only JPQL UPDATE on the row; every other write is a versioned `save` or
a delete), but stated nowhere. Smallest fix: describe the two-step
decomposition here and name the bump-on-every-write invariant the
refinement rests on, so a future unconditional UPDATE is recognizable as
breaking the verified abstraction. Defense-in-depth alternative (not
demanded): also condition the JPQL on the expected metadataLocation.

### Comment 3
- path: specs/tla/README.md, line 54 (RIGHT)
- body:

[tla-review][blocking] This walkthrough is introduced as "the abridged
`NoSnapshotLoss` counterexample from `tlc-rename-unguarded.out`", but the
committed log's step order differs: the trace runs `Load(w1)`,
`WriteMetadata(w1)`, `RenameLoad`, `HtsCommit(w1)`, `RenameWriteMetadata`,
`RenameHtsUnguarded`, while the list here puts `RenameLoad` first. The two
orders are semantically interchangeable (the commuted actions are
independent), but a reader diffing this text against the log will conclude
one of them is stale. Smallest fix: reorder the numbered steps to match the
committed trace.

### Comment 4
- path: services/housetables/src/main/java/com/linkedin/openhouse/housetables/api/handler/OpenHouseUserTableHtsApiHandler.java, line 124 (RIGHT)
- body:

[arch-review][follow-up] The concurrency token rides in a repurposed DTO
field: `fromUserTable.metadataLocation` here means "the location the caller
observed", and only the comment above says so — nothing in the
`renameEntity(UserTable, UserTable)` signature does. A future maintainer
who populates `fromUserTable.metadataLocation` from the stored row "for
completeness" disables the token check silently, with no compile-time
signal. A dedicated `expectedMetadataLocation` parameter on the handler's
rename seam (touching the generic handler interface and its Jobs
implementation, all inside services/housetables) would make that misuse
unrepresentable.

### Comment 5
- path: iceberg/openhouse/internalcatalog/src/test/java/com/linkedin/openhouse/internal/catalog/repository/HouseTableRepositoryImplTest.java, line 364 (RIGHT)
- body:

[testing-review][follow-up] This asserts only
`getPath().contains("expectedMetadataLocation=")` — it stays green if the
client sends an empty or wrong value, which is precisely the regression
that would silently disable the HTS token check this PR adds. One-line
strengthen: assert the decoded query-parameter value equals
`HOUSE_TABLE.getTableLocation()`.

### Comment 6
- path: services/tables/src/test/java/com/linkedin/openhouse/tables/e2e/h2/HouseTablesH2Repository.java, line 47 (RIGHT)
- body:

[testing-review][follow-up] This conflict branch (and its twin in
tables-test-fixtures) is fake behavior no test exercises: every
services/tables e2e rename takes the happy path, so the fixtures' fidelity
to the real HTS 409 semantics is never checked. If the guard here drifts
from HTS, the tables e2e suite stays green while real deployments behave
differently. Named test: a services/tables e2e case that advances a table's
HTS row, drives a rename with a stale token through the catalog, and
asserts the surfaced conflict; or, cheaper, a fixture-level test pinning
the mismatch throw.

### Comment 7
- path: services/housetables/src/main/java/com/linkedin/openhouse/housetables/repository/impl/jdbc/UserTableHtsJdbcRepository.java, line 130 (RIGHT)
- body:

[arch-review][follow-up] The 0-rows conflict outcome exists only as an
`int` the caller must remember to check; the javadoc states the obligation
but nothing enforces it, and one in-tree caller already ignores the return
(`HtsRepositoryTest#testRenameCaseSensitivity`). A second production caller
that skips the check reopens the lost-update class one layer down. One-line
hardening: annotate with `@CheckReturnValue` so a discarded result is
flagged at compile time.

### Comment 8
- path: services/housetables/src/main/java/com/linkedin/openhouse/housetables/services/UserTablesServiceImpl.java, line 174 (RIGHT)
- body:

[arch-review][follow-up] Both new conflict throws attach a message-less
`new RuntimeException()` as cause, and `OpenHouseExceptionHandler` renders

### Comment 9
- path: iceberg/openhouse/internalcatalog/src/main/java/com/linkedin/openhouse/internal/catalog/repository/HouseTableRepository.java, line 46 (RIGHT)
- body:

[arch-review][follow-up] The javadoc promises the rename "fails with a
concurrent update conflict" without naming
`HouseTableConcurrentUpdateException` — the type `doCommit`'s catch builds
its retry policy on. With three implementations of this interface (the impl
plus two H2 fixtures), an implementer signaling the conflict with a
different unchecked type would escape that catch as a non-retriable
failure. Zero-blast-radius fix: add
`@throws HouseTableConcurrentUpdateException` to the javadoc.

### Comment 11
- path: services/housetables/src/test/java/com/linkedin/openhouse/housetables/e2e/usertable/HtsRepositoryTest.java, line 280 (RIGHT)
