  fixture's own `rename` default method** — `Mockito.mock(type, CALLS_REAL_METHODS)`

**The preferred catalog-driven e2e is not constructible without stubbing** —
verified empirically, not assumed. I wrote it first (create table, `loadTable`,
open the rename transaction, advance the HTS row with a real second commit, then
`commitTransaction`) and it committed cleanly. Cause: Iceberg refreshes the
table operations immediately before the commit lands
(`BaseTransaction.commitSimpleTransaction` and `PropertiesUpdate.apply` both call
`ops.refresh()`), so the rename's declared base is re-read from the
already-advanced row and no stale token ever reaches the fixture. That failing
test was removed rather than propped up with a spy; the finding and the cause
are recorded in the commit message and the PR body. It is also a mildly useful
narrowing result about the real-world window.

### 10. Tokenless mode in TLA+ — **FIXED. TLC produces the counterexample.**

Spec: `RenameToken` joins `RenameGuard` (read only when `RenameGuard = TRUE`).
New variable `rSeen` and rename state `"read"`; new actions `RenameHtsRead`
(the HTS service's own `findById`), `RenameHtsTokenless` (the UPDATE,
conditional only on the row still being at `rSeen`), and
`RenameHtsTokenlessConflict`. The two HTS steps are split here precisely
because the token-present model's atomic collapse is unavailable without a
token. `RenameHtsGuarded`/`RenameHtsConflict` are now gated on `RenameToken`;
`RenameCrash` accepts the new state; `rSeen` threaded through every UNCHANGED.

**TLC results (OpenJDK 21, scratchpad `tla2tools.jar`, each run ≤ 1s):**

| Config | Invariants | Result | States |
|---|---|---|---|
| `rename_unguarded.cfg` | TypeOK, NoSnapshotLoss | **NoSnapshotLoss VIOLATED**, depth 7 | 348 / 183 distinct |
| `rename_unguarded_version.cfg` | TypeOK, MonotonicVersion | **MonotonicVersion VIOLATED**, depth 4 | 48 / 28 |
| `rename_guarded.cfg` | TypeOK, NoSnapshotLoss, MonotonicVersion | **No error**, complete graph, depth 18 | 18,135 / 6,130 |
| `rename_tokenless.cfg` (new) | TypeOK, NoSnapshotLoss | **NoSnapshotLoss VIOLATED**, depth 8 | 716 / **351** |
| `rename_tokenless_version.cfg` (new) | TypeOK, MonotonicVersion | **No error**, complete graph, depth 18 | 28,095 / **9,806** |

The three pre-existing runs reproduce bit-for-bit (same state counts, same
depths) after the spec edit; their logs were re-captured because the traces'
`line N` annotations shifted.

**The residual counterexample** (`tlc-rename-tokenless.out`), steps 1–5
identical to the unguarded trace, then:

6. `RenameHtsRead` — HTS reads the row itself, sees location 1 / version 1
   (`rSeen = 1`). Nothing compares that to the renamer's base (`rBase = 0`).
7. `RenameHtsTokenless` — the CAS on `rSeen` matches, so the UPDATE lands:
   `catLoc = 2`, `catSnaps = {}`, **`catVer = 2`**.
   `everCommitted = {w1} ⊄ catSnaps = {}`.

**The sharpest finding is the companion run.** `MonotonicVersion` *holds* in the
tokenless mode across the complete 9,806-state graph. So a tokenless rename that
drops a committed snapshot is indistinguishable, by the version column alone,
from a legitimate commit — whereas the unguarded rename at least leaves a
rewritten row at an unchanged version. The residual window is narrower than the
unguarded one and leaves *less* forensic evidence.

README rewritten: leads with the result (which also closes the unassigned
"lead with the result" follow-up, comment 12), presents all five runs as three
modes, keeps the refinement caveat, and adds the tokenless trace walkthrough
alongside the unguarded one. Repro commands cover all five configs.

**Operational implication stated in the PR body:** close the null-token mode —
HTS should reject a rename declaring no base, leaving only the verified-safe
token-present mode. Gated on (a) client rollout, which needs a metric counting
tokenless renames at the HTS endpoint reading zero for a window, since the
parameter is optional today precisely so old clients keep working; and (b) the
`INITIAL_VERSION` fallback in `OpenHouseInternalTableOperations` — legacy tables
with no persisted `tableLocation` have no base to declare and need a backfill,
or an explicit "no base exists" token distinguishable from "caller omitted the
base", before the requirement can apply to them.
